Claude responded: This is very doable, but there's a key thing to understand about how Rego works: OPA won't give you this structure for free — you have to author the policy to …

This is very doable, but there's a key thing to understand about how Rego works: OPA won't give you this structure for free — you have to author the policy to produce it. Rego has no built-in notion of "which inputs did this rule touch," and boolean rules like nut_free are undefined (absent from output) when they fail, not false. So the pattern is to make the report an explicit rule.

Quick note on your sketch first: you've got temp_ok twice (the second should be time_ok), and JSON doesn't allow trailing commas — but the shape is exactly right.

Here's a version of the bakery policy that emits it:

rego 
package bakery

import rego.v1

# --- predicates, with defaults so failure = false, not undefined ---

default nut_free := false
nut_free if not "nuts" in input.allergens

default temp_ok := false
temp_ok if {
    input.bake.temp_c >= 175
    input.bake.temp_c <= 200
}

default time_ok := false
time_ok if {
    input.bake.minutes >= 25
    input.bake.minutes <= 40
}

default compliant := false
compliant if {
    nut_free
    temp_ok
    time_ok
}

# --- structured evaluation report ---

report := {
    "compliant": compliant,
    "predicates": {
        "nut_free": {
            "inputs": [{"name": "allergens", "value": object.get(input, "allergens", [])}],
            "passed": nut_free,
        },
        "temp_ok": {
            "inputs": [{"name": "temp_c", "value": object.get(input, ["bake", "temp_c"], null)}],
            "passed": temp_ok,
        },
        "time_ok": {
            "inputs": [{"name": "minutes", "value": object.get(input, ["bake", "minutes"], null)}],
            "passed": time_ok,
        },
    },
}

Then:

bash 
opa eval -d bakery.rego -i input.json --format=pretty 'data.bakery.report'

gives you exactly your JSON (with time_ok fixed). From this structure, rendering the human-readable step 3 table is a trivial post-processing job — the report is the source of truth, the table is presentation.

A few design points worth calling out:

Defaults matter. Without default temp_ok := false, a failing or missing-input predicate simply vanishes from the output, and your report rule would itself become undefined if it referenced an undefined value. The default declarations plus object.get for the echoed inputs make the report total — you always get a complete document, even for a non-compliant or malformed input. That's important for an evidence trail: "failed because temp_c was missing" should still produce a report.

The "inputs used" are declared, not discovered. You're duplicating the knowledge of which fields each predicate reads. That's a real maintenance cost, but it's also arguably a feature for unified evidence — the report schema is an explicit contract, stable across policy refactors. If you want to reduce drift, one pattern is to define each clause as a single object and derive everything from it:

rego 
clauses["temp_ok"] := {
    "passed": temp_ok,
    "inputs": [{"name": "temp_c", "value": object.get(input, ["bake", "temp_c"], null)}],
    "expression": "temp_c >= 175 and temp_c <= 200",
}

with report := {"compliant": compliant, "predicates": clauses}. Adding an "expression" string per clause gets you the "evaluated expression" column from the table too.

Alternatives that don't quite work. opa eval --explain=full gives you a trace of every expression evaluated, which technically contains this information, but it's verbose, unstable across OPA versions, and painful to parse — fine for debugging, wrong for evidence. Evaluating the whole package (data.bakery) gets you the rule values but hits the undefined-on-failure problem and gives you no input echo. The explicit report rule is the idiomatic answer, and it has a nice property for your use case: the report itself can be hashed and attested alongside the policy hash and attestation set hash, so the "workings" are as verifiable as the verdict.

One thing to decide early: whether inputs should echo values from input (what was evaluated) or reference attestation IDs (where the value came from). For unified evidence you probably want both — e.g. {"name": "temp_c", "value": 180, "attestation": "att-003"} — which means threading attestation provenance into the evaluation input document rather than flattening it away.

Yes — and it works cleanly. I built and verified a working version with OPA 1.18. The core idea: customers define clauses as data (path + operator + params), and your library is a generic engine that evaluates them and emits the report. Both files are attached, tested against passing and failing inputs.

What the customer writes shrinks to essentially this:

rego 
package bakery
import data.kosli.evidence

clauses := {
    "nut_free": {"path": ["allergens"], "op": "excludes", "value": "nuts",
                 "description": "Must not contain nut allergens"},
    "temp_ok":  {"path": ["bake", "temp_c"], "op": "range", "min": 175, "max": 200},
    "time_ok":  {"path": ["bake", "minutes"], "op": "range", "min": 25, "max": 40},
}

report := evidence.report(input, clauses)

No evaluation logic, no report plumbing, no default incantations — the library handles totality, input echoing, and even auto-generates the "evaluated expression" strings from the specs. The verified output for the failing case shows every predicate present with passed: false and the offending values echoed (including "value": null for a missing field), which is exactly what you want for an evidence trail.

A few design decisions worth flagging:

Rego forces the data-driven design, and that's good news. Rego has no first-class functions, so you can't have customers pass predicates as callbacks. Instead the library defines an operator vocabulary — range, excludes, includes, equals, present — as multiple bodies of one op_passed(spec, value) function, with default op_passed(_, _) := false making evaluation total. This constraint is actually the product insight: since clauses are pure data, they don't have to live in Rego at all. Customers could define them in JSON/YAML in your UI, and Kosli can hash them (your policy hash becomes a hash of the clause set), diff them across versions, render them as human-readable policy without parsing Rego, and validate them against a JSON Schema. The Rego library becomes an implementation detail.

You still need an escape hatch. Real policies outgrow any operator vocabulary. The pattern I used: {"op": "custom", "passed": my_rule, "inputs": [...], "expression": "..."} — the customer writes arbitrary Rego for the boolean, but registers it in the clause map so it still lands in the report with declared inputs. The trade-off is that for custom clauses, "inputs used" is self-reported rather than derived.

Totality is where the bugs hide. My first run silently dropped the custom clause because it had no path key — spec.path was undefined, which made the comprehension entry vanish and corrupted compliant. This is the sharpest edge in Rego for exactly this use case: undefined propagates silently. The fix is defensive object.get everywhere in the library, and it's precisely the kind of thing worth solving once in a library rather than letting every customer rediscover. I'd also ship opa test cases asserting that malformed specs and missing inputs still produce complete reports.

Distribution. Package it as an OPA bundle — opa build the kosli.evidence package and publish to an OCI registry, so customers pull a pinned version and import data.kosli.evidence. Bundles can be signed, which fits your attestation story: the library version and hash become part of the evidence ("evaluated with kosli.evidence v1.2.0, digest sha256:..."). Also run opa check --strict in CI on customer clause files.

One open question for the vocabulary design: whether operators should reference attestation IDs rather than raw paths — e.g. {"attestation": "att-003", "field": "temp_c", ...} — so provenance flows into the report automatically ("inputs": [{"name": "temp_c", "value": 180, "attestation": "att-003"}]). That means the evaluation input document keeps attestation structure instead of flattening it, but it would make the step-3 table fully traceable back to section 1 without any joining logic outside Rego.

Claude responded: You need the OPA binary, then it's one command.

You need the OPA binary, then it's one command.

1. Install OPA (single static binary, no dependencies):

bash 
# macOS
brew install opa

# Linux
curl -L -o opa https://openpolicyagent.org/downloads/latest/opa_linux_amd64_static
chmod +x opa && sudo mv opa /usr/local/bin/

2. Run it from the directory containing the four files:

bash 
opa eval -d library.rego -d bakery.rego -i input.json --format=pretty 'data.bakery.report'

That's it — -d loads each policy file, -i is the input document, and the final argument is the query (the report rule in the bakery package). Swap -i input.json for -i bad_input.json to see the non-compliant report.

A couple of variations you'll probably want:

bash 
# Load everything in the directory instead of naming files
opa eval -d . -i input.json --format=pretty 'data.bakery.report'

# Just the verdict
opa eval -d . -i input.json --format=raw 'data.bakery.compliant'

# Pretty JSON without the eval wrapper (raw gives you clean output for piping)
opa eval -d . -i input.json --format=raw 'data.bakery.report' | jq .

Note that -d . loads every .rego and .json file in the directory tree — the JSON files get mounted under data, which is harmless here but can surprise you; naming the files explicitly is more predictable.

Also worth knowing: opa check --strict . lints the policies, and if you iterate on this, opa run . drops you into an interactive REPL where you can poke at data.bakery.report directly after setting the input with input := {...}.

Claude responded: That's the -d .

That's the -d . gotcha biting: it loads every file in the directory as data — including input.json and bad_input.json. Both land at the root of data, both contain allergens and bake keys, and OPA refuses to merge the conflict.

Three ways to fix it, pick one:

bash 
# 1. Name the policy files explicitly (most predictable)
opa eval -d library.rego -d bakery.rego -i input.json --format=raw 'data.bakery.compliant'

# 2. Tell OPA to ignore the input files when loading
opa eval -d . --ignore='*.json' -i input.json --format=raw 'data.bakery.compliant'

# 3. Restructure: keep policies and inputs apart
#    policies/library.rego, policies/bakery.rego, inputs/input.json
opa eval -d policies/ -i inputs/input.json --format=raw 'data.bakery.compliant'

Option 3 is the layout you'd converge on anyway once this grows — it also makes opa test policies/ and opa check --strict policies/ clean. And it mirrors the conceptual split you actually care about: policies are the hashable, versioned thing; inputs are per-evaluation evidence.

All verified end to end. The schema and the machinery that emits it:

Row schema. Each result row is {subject: {type, id}, predicate, description, expression, inputs, passed}. The natural primary key is (subject.id, predicate), which makes the pivots you described trivial — jq 'group_by(.subject.id)' for per-commit reporting, group_by(.predicate) for "independence across the change". Two schema decisions worth making deliberately:

  • subject is a typed reference, not the subject data. The row carries {type: "commit", id: "d4e5f6"} plus only the fields the predicate actually read (in inputs). Full subject data stays in the evaluation input document, which you're presumably attesting anyway — repeating it per row would bloat the report and create two sources of truth.
  • inputs echoes both sides of comparisons. For reviewer ne author the row shows both values, so a failed row is self-explanatory without going back to the input: [{name: "review.reviewer", value: "bob"}, {name: "author", value: "bob"}].

Policy shape. A policy becomes a list of subject sets: {type, path, id, min_count, clauses} where the collection path resolves against the input root, and all clause paths resolve relative to the subject. That relative-path rule is what makes clauses reusable across policies — independent_reviewer doesn't know or care where the commits collection lives. The bakery needed no special-casing: path: [] makes the input root a single subject, and its report comes out in the identical row shape with subject: {type: "batch", id: "cake-batch-2026-03-18-001"}.

New operators. Cross-subject-field comparison needed two: compare ({op: "compare", cmp: "ne", left: [...], right: [...]}) and compare_time, which parses RFC3339 via time.parse_rfc3339_ns so you're comparing instants rather than strings — and a malformed timestamp fails the clause rather than erroring, preserving totality.

The vacuous-truth trap, handled uniformly. every over an empty collection passes, so a change with zero commits would sail through review policy — clearly wrong for evidence. min_count on the subject set fixes this, and the nice property is that the guard is expressed as a row in the same schema (predicate: "min_count", subject.id: null, inputs: [{name: "count(commits)", value: 0}]), so downstream consumers don't need a second code path for collection-level checks. You can see it failing correctly in the empty-input run above. I'd suggest defaulting min_count: 1 in your product layer and making customers explicitly opt into "empty is fine".

Two things that changed from v1, worth noting:

The custom-clause escape hatch got harder. In v1 a custom clause embedded a pre-computed boolean; that doesn't work per-subject, because the customer's rule now needs to run against each subject, and Rego can't pass functions as data. The idiomatic replacement: customers extend the operator vocabulary by adding op_passed bodies to the kosli.evidence package from their own file (Rego allows contributing rule bodies to another package across files). That's a well-trodden pattern in data-driven Rego engines, and it keeps custom logic flowing through the same report machinery — but it does mean custom ops are library-level extensions rather than inline one-offs, which is probably the right governance trade-off for evidence anyway.

Determinism for hashing. Row order is subject order (array order in the input) × clause name (Rego iterates object keys sorted), with meta-rows first. That's stable given the same input and policy, so the report itself can be hashed and attested. If subjects might arrive in nondeterministic order upstream, sort the collection before evaluation rather than in the report.

One schema question to settle before you freeze it: whether rows should also carry a clause field echoing the spec that was evaluated ({op: "compare", cmp: "ne", ...}). It's redundant with the policy hash, but it makes each row independently interpretable without dereferencing the policy — for a unified-evidence format consumed by other processes, I'd lean toward including it.

This policy is a great stress test, because it breaks two assumptions baked into v2:

  1. The quantifier is existential. compliant_pr_exists needs some merged PR satisfying all clauses — v2 only knew "every subject passes". Notice your whole "split across PRs" catch-all violation exists because hand-rolled per-condition checks each quantify independently (some pr... approved, some pr... signed). With per-subject rows and a some quantifier, that failure mode becomes structurally impossible — the report shows each PR's row set, and the verdict requires one PR to clear everything.

How the hand-written policy maps onto the report machinery:

Structure → subject sets. Your policy is two implicit subject sets. The artifact-level gates (fingerprint recorded, attestation COMPLETE) become an every-quantified set over the single artifact. The per-PR conditions become a some-quantified set over PRs with where: state == MERGED — which is the direct encoding of your compliant_pr_exists comment: "requirements cannot be split across different PRs" is now a property of the quantifier rather than a rule you had to remember to write.

Violations become a projection of the report. The whole violations contains ... block collapses to five lines: failed rows of unsatisfied sets. The satisfied-set condition is the subtle part — under some, a failed row is not a violation if another PR cleared everything, which your hand-written version handles by having each violation independently re-derive artifact state. And your carefully-sequenced cascade (only report "no merged PR" if attestation is COMPLETE, etc.) stops being control flow: the rows carry the data, and any consumer can apply whatever precedence it wants at render time. Meanwhile output := {allow, violations, report} keeps the shape kosli evaluate expects — the report is purely additive.

The catch-all violation gets deleted, and its replacement is strictly more informative. Your split-across-PRs clause can only say "no single PR satisfies everything together." The report says which requirement each candidate PR failed, with the offending values inline. That's the payoff of the flat row schema: the diagnostic your catch-all couldn't express falls out for free.

What the library had to grow (all in the attached v3): per-set quantifier (every/some) with set-level verdicts in the report — necessary because under some, compliant can no longer be derived from rows alone; a where filter so non-merged PRs aren't subjects; an all/any collection operator for commits_signed — note this supports exactly one nesting level, because Rego forbids recursion, so the quantified ops delegate to a separate leaf_passed function (a real, documented limit of the DSL); and the custom-op extension mechanism proven in anger: peer_approved is eleven lines in a package kosli.evidence file on the policy side, flowing through the same rows as everything else, with expression and echo supplied by the clause since the library can't introspect custom logic.

One honest gap versus your original: unverified_commit_details produced triage-grade output — short SHA paired with raw signature_state. The generic echo gives commits[].verified = [true, false], which tells you that and how many, but not which commit. If that pairing matters (it probably does for triage), either set "echo": [["commits"]] on the clause to dump the commit objects into inputs, or keep a bespoke diagnostic helper alongside — the schema doesn't prevent it, it just doesn't generate it. That's the general shape of the trade: the DSL generates uniform, hashable, pivotable evidence; hand-tuned prose diagnostics remain a deliberate add-on per clause.
